# EDU-0046 — R42-F01 token redemption authority

## Scope and invariants

- Recheck the token issuer at redemption time, after the target user and token are locked and before password/status changes.
- Require the issuer still to hold the purpose-specific global permission and to cover every active, unrevoked, unexpired target grant, including future-start grants.
- Failure is indistinguishable from an invalid token: HTTP 400 `ACCOUNT_TOKEN_INVALID`, limiter failure recorded, no password/status/session/audit mutation committed.
- Preserve F04 row-lock ordering, single-use behavior, positive reset/invitation paths and `issued_by` audit attribution.
- Do not decide whether a suspended issuer invalidates a token when its grants remain present; document this as a Security Owner question.

## Security semantics handed to the reviewer

- Redemption now locks the target user and token, then loads the issuer's current started grants. Reset requires current global `user:password_reset`; invitation requires current global `user:create`.
- The issuer must cover every active, unrevoked and unexpired target grant, including grants whose `valid_from` is in the future. This reuses the same containment rule as the admin issue/status paths.
- Rejection remains the generic `ACCOUNT_TOKEN_INVALID` and increments the existing account-token rate limiter. The transaction rolls back, so password, account status, sessions, token `used_at` and audit rows are unchanged.
- A rejected token is not permanently consumed. It can become usable again before expiry if issuer authority is restored and target coverage is satisfied. This avoids irreversible mutation on a generic failure but must be confirmed by the independent reviewer/Security Owner.
- Whether `suspended`/`locked` issuer account status alone must invalidate a token remains unresolved. No new status policy was invented in this task.
